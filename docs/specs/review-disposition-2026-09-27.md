# Disposition of the second full review

This records design decisions and the later specification coverage audit, not
implementation results. The proposal is revision 2.6. The feature specs
remain drafts until planning and implementation validate their contracts.

| Review issue | Decision and location |
| --- | --- |
| Missing plan, validity, comparison, predictive, artifact, and authorization states | Accepted. The canonical state vocabulary now names these dimensions and transitions; 008, 013, 016, 017, and 019 own their domain rules. |
| Inquiry stopping and mechanical versus semantic judgment | Accepted. The terminal precedence rule is canonical; 012 records worker reasoning while the controller checks bindings and policy. The access and judgment contract assigns disputed meaning to a named reviewer or owner. |
| Undefined principals and access scope | Accepted. The access and judgment contract defines identity, roles, grants, deny-by-default behavior, and controller, adapter, catalog, and viewer enforcement. 001 tests the boundary; 011 labels local shell limits honestly. |
| Overlapping catalog, ledger, and answer retrieval | Accepted. README and 019/020/023 assign one owner to the index, attempts, and card ranking respectively. |
| Duplicate milestone requirements | Accepted where behavior diverged. 002 and 005 now explicitly consume focused feature contracts; their FRs remain integration obligations. |
| Conflicting no-progress and exact-repeat keys | Accepted. 012 uses 023's complete analytical identity and handles unknown dimensions separately. |
| Repeated looks and practical margins | Accepted. 016 owns the shared inspection contract; 006/013 bind their method parameters to it. Favorable-direction gain and `delta` are defined in 013 and the canonical vocabulary. |
| Missing enforceable demo budget | Accepted. 012 and the proposal declare count and command-timeout limits. Active cancellation and monetary/resource caps are advertised only after an adapter proves enforcement. |
| Wrong predictive direction and overpowered null fixture | Accepted. 013 transforms both metric directions to favorable gain, separates a tight below-margin case from a low-power null case, and records the three classifications canonically. |
| Worker-authored tests auto-activate skills | Accepted. 022 requires an independent policy-owned check for low-risk method activation and owner review for changed definitions, expanded audience, access rules, and release policy. |
| Fixture/evaluator ownership and small sample claims | Accepted. 018 owns versioned fixtures and the reference evaluator from the first slice. Three-run feature checks are smoke tests; the 20-case gate is limited to its frozen profile. A broad reliability claim needs a separate predeclared design. |
| Legacy import without a prior key-cardinality declaration | Accepted. 007/019 preserve unknown historical provenance; a new supported transformation must declare and validate grain. |
| T-case and invariant overclaims, green checklists | Accepted. The traceability audit identifies one primary owner for T01–T61, several spec traces were narrowed, and unsupported blanket checklist attestations were reopened. The follow-up pass mapped all 234 FRs and 114 edge cases to numbered checks, corrected missing fixtures, and checked structural references with `scripts/audit_spec_coverage.py`. |
| Local-first crash safety, compare-and-swap, and sheet permission | Retained. These are testable local correctness properties. Strong source secrecy requires source or host permissions outside a shell that can read the bytes; the product labels workflow-only boundaries. |
| Lexical-first retrieval versus Hit@3 target | Retained as a falsifiable target. A lexical implementation may fail it; the frozen labels and threshold must not be softened after evaluation. Ranking can change without changing the acceptance question. |
| Analytics isolation as the first milestone | Retained. 001 now requires actual removal of reachable factory prompts and templates at completion and disables generic retry behavior. A context-only filter is an explicitly incomplete migration stage. |
| Inferential profile forced behind use review | Accepted. 006 now depends on 003 and 016's repeated-inspection contract, not on completion of 005's consequential-use integration. |

The follow-up pass added explicit fixtures for malformed check output,
post-check edits, permission changes, nested work allowances, benchmark
leakage, notebook replay, exact-repeat identity, and append-only ledger
history. It also defined a 48-signal, pre-labeled candidate-detection fixture
and initial precision and recall gates. The six milestone planning-readiness
boxes were checked after the coverage audit. Checked quality boxes attest to
specification readiness; they are not software test results.
