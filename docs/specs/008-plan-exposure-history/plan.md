# Implementation Plan: Preserve Plans and Outcome Exposure

**Branch**: `008-plan-exposure-history` | **Date**: 2026-09-28 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/008-plan-exposure-history/spec.md`

## Summary

Implement the immutable, typed Plan and exposure boundary for each inquiry. Registration validates the four frozen Plan profiles against the schemas generated by feature 001. Locking creates a content identity; any edited locked registration forks a linked revision. The controller classifies changes to locked analytical fields as substantive, keeps code-only corrections on a new Execution, and derives the canonical plan interpretation from the lock, declared inspection rule, and durable exposure history. The 008 facade exports typed request/result hooks for 003 to compose: registration, lock and change assessment, commit-before-release exposure, and committed-history rehydration. An exposure-release permit is returned only after 009 confirms `committed` or `replayed`. A replacement-context projection preserves the committed history for 003; 008 does not claim that its acceptance test delivered that projection to a live replacement worker.

The feature writes only `src/analytics/plans.ts`, `src/analytics/exposure.ts`, and `src/analytics/acceptance/008.test.ts`. It uses 009 for append-only evidence commit/recovery and the existing controller context's committed-read capability; it does not create a second store or edit the 003 controller. All demonstration cases use the locked synthetic/local fixtures.

**Testing**: `pnpm typecheck` and `pnpm test` for intermediate units, then the feature acceptance suite. Acceptance calls the production 008 facade with synthetic/local fixtures and the actual 009 commit/recovery and `executeStageV1` services. It verifies that rejected or conflicting exposure commits return no release permit and cause no stage invocation. It validates the 008 rehydration result shape and retained labels, without constructing a fake controller or requiring a live delegated inquiry. Feature 003 owns assertions that the actual controller supplies that result to a replacement worker.

**Target Platform**: Local TypeScript analytics controller with the execution and persistence guarantees described in `docs/build/ARCHITECTURE.md`.

**Project Type**: Internal TypeScript analytics product library and controller capability.

**Performance Goals**: Plan registration and exposure lookup remain bounded by committed inquiry history; no independent search index is introduced. No separate latency target is specified for this record-scale feature.

**Constraints**: Strictly consume generated mode schemas; reject unsupported profiles and unknown schema fields. Preserve immutable digests, stable refs, earlier exposure, and worker/reviewer attribution. Mark out-of-tool access unknown where it cannot be observed. Do not claim that workflow withholding isolates files from a local worker shell. Keep the shared interface freeze, feature graph, feature spec, checklists, thresholds, and reference answers unchanged.

**Scale/Scope**: One inquiry with a bounded number of Plan revisions and exposure events under the frozen fixture budget. The controller's existing revision and work allowances remain authoritative.

## Design Decisions

1. **One normative mode contract.** Use only the generated Pydantic schemas for `ExploratoryPlanV1`, `DescriptivePlanV1`, `PredictivePlanV1`, and `InferentialPlanV1`. TypeScript validates through the generated schema adapter and shared vectors. Causal and other unimplemented modes return the explicit unsupported-profile limitation.
2. **Immutable lock and fork.** Registration can be revised before lock. Lock binds the exact payload digest. Any change after lock creates a new Plan ref linked to its predecessor. Deterministic comparison of the locked fields catches substantive changes; the worker supplies an attributed reason, and the controller records that reason with the mechanical field diff. Unknown semantic classification stays unresolved.
3. **Separate analysis identity from program identity.** Population, target, comparison/method, partition design, search space, and stopping rule are Plan identity. A code-only repair keeps that Plan ref, creates a new Execution and code digest, and records which outcomes had already been seen.
4. **Commit exposure before release.** The 008 exposure hook appends an exposure record before 003 returns a metric, result summary, skill reference containing a result, or evaluation output to a worker. Only a `committed` or `replayed` result yields an exposure-release permit; `rejected` and `revision_conflict` yield a blocked result with no permit. Observed, self-reported, and unknown access are distinct. An unknown record is never interpreted as no access.
5. **History is read through the host.** 009 owns committed manifests and recovery. The 003 invocation context supplies committed reads. 008 consumes a controller-supplied committed inquiry-history snapshot and validates record refs, revisions, digests, and access-safe summaries; it does not invent an 009 file-reading API or read sidecar paths directly.
6. **Restart uses durable facts, not summaries.** The 008 rehydration hook returns a typed Plan/exposure projection from committed history. 003 uses that result to construct each replacement-worker context, includes stable refs and the full relevant timeline, and records its digest. A shortened worker-authored summary cannot remove those fields. The 008 acceptance verifies the projection contract; the full context delivery assertion belongs to 003.
7. **Confirmation is boundary-specific.** A plan on a genuinely fresh evaluation partition may be confirmatory only if the partition boundary and no-prior-access guarantee are recorded. Workflow withholding on a shell-readable local fixture is not such a guarantee. Development outcomes remain visible in the lineage.

## Controller and Acceptance Boundary

The accepted graph places feature 008 before feature 003; 003 owns `controller.ts` and the `AnalyticsExtensionV1` lifecycle. Feature 008 exports typed request/result APIs from its production facade for 003 to compose through the frozen lifecycle callbacks:

| 008 facade operation | Request/result boundary | 003 composition point |
| --- | --- | --- |
| `registerPlanV1` | Registration request → validated registered Plan or explicit unsupported/invalid result | Worker-authored Plan admission |
| `lockPlanV1` | Plan ref and exposure snapshot → immutable locked Plan | Before stage admission |
| `assessPlanChangeV1` | Prior Plan, proposed registration, code digest, and attributed worker reason → mechanical change assessment and linked Plan or implementation-only Execution decision | Before revised stage admission |
| `commitExposureBeforeReleaseV1` | Exposure and release target → committed exposure ref plus permit, or blocked result without a permit | Before outcome-bearing context material is returned or a follow-on stage is invoked |
| `rehydratePlanExposureV1` | Controller-supplied committed inquiry history → validated Plan/exposure projection and completeness status | Orientation/replacement-context construction |

The acceptance test calls these real 008 exports with synthetic/local fixtures and invokes 009's production `executeStageV1` only after a successful exposure result. It uses 009 publication results for committed, replayed, rejected, and revision-conflict cases; rejection/conflict must return no permit and leave the stage invocation count at zero. The rehydration assertions validate the facade's projection at its boundary. They do not instantiate a controller, simulate a delegated worker, or claim that a worker received the projection.

Feature 003's downstream acceptance must compose these exact request/result APIs through its actual `controller.ts`/CLI and verify T06, T07, T09, and T61, including context delivery to a replacement worker. Feature 008 records that integration as downstream evidence when available; it must not claim its facade test proves full 003 integration or enforced holdout isolation.
